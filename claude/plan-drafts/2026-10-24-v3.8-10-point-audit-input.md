## Executive decision

**Combine the 10 findings into one finite correction pass, then freeze the plan.** The first five (A1-A5) are **draft correctness and retention-design defects**. The next five (B1-B5) are **execution and career-conversion risks**. These are separate categories: a perfectly checked curriculum can still fail if there is not enough completed work or employer-facing proof.

Do not introduce another track or run a complete curriculum redesign. Prioritise blocking prerequisites, credible use evidence, realistic weekly execution, earlier external feedback, and an employer-facing ownership fallback. Retain the existing November 15, 2026 measured reforecast.

## Part A. Five drafting and retention defects from the first review

### A1 | HIGH | P1 requires SQL mechanisms not yet taught

**Evidence from v3.8:** The W5-W8 P1 row requires at least one query using `IN` and one using a subquery, describing these as reuse of September work. However the section 2 SQL baseline explicitly says **`IN` and subqueries are new**. P2 is scheduled much later, beginning W22. The checker only protects a short, fixed list of technical terms, and does not catch this contradiction.

**Roadblock:** A coach could ask Om to implement and explain an untaught construct, then call the result a failure of understanding. This repeats the very sequencing problem v3.8 is meant to remove.

**Minimal correction:** Either (a) teach two tiny SQL examples with their actual prerequisite time *before* using them in P1, then use them in the repository with passing tests; or (b) drop the P1 demand and use those constructs when P2 teaches them. Do not claim they were already taught in September.

**Time / trade-off:** Option (b) requires no additional learner hours and no gap in P1's actual database objective. Option (a) needs a learner-level estimate and a named displaced task or later date; do not hide this in P1's already full hours. **Evidence to close:** one correct small example and its own explanation before a scored query that depends on it.

### A2 | HIGH | The checker cannot prove the promised real-code use

**Evidence from v3.8:** Section 6 promises a **"Use in real code within 7 days"** step for each teaching part. The v3.8 Python checker checks for literal wording such as `Use in` or `Use on kind` only in a selected set of lane labels. It does **not** inspect actual test execution, a changed production/project file, a commit, or the seven-day completion window. For example, W4 L1's "Use in PRCP" is to *name* relationships and a coupling problem in a note, which is an explanation, not necessarily executable use.

**Roadblock:** The plan can appear protected by a green checker while a learner completes explanations and katas without ever transferring the idea into running project code.

**Minimal correction:** Assign each use step a truthful type: **CODE** = target file + test or kind proof + commit; **EXPLAIN** = a diagram, trace or short note plus oral defence for knowledge-only concepts. Require evidence at the unit review, and record the date. Keep the script for structural coverage, but do not claim it verifies real-world execution. A seven-day rule must be checked against dated evidence, not the existence of words in the week row.

**Time / trade-off:** Code use is already meant to be inside the unit budget. Where a current note is upgraded to tested code, estimate the actual extra minutes and displace something explicitly; otherwise relabel it as EXPLAIN. **Evidence to close:** coach can point to the exact changed artifact, its run, and Om's explanation.

### A3 | HIGH | Teaching, application and verification are crammed into 15-minute fragments

**Evidence from v3.8:** W11 has a `L3 0.25h` segment naming Strategy, Factory and Observer, replacing an `if` chain in PRCP and showing green tests. W19 has a `K5 0.25h` segment naming ConfigMap, Secret, ServiceAccount and RBAC with use on kind. The checker emits fragmentation warnings but not failures. These row descriptions may span a longer multiweek unit, yet read as though the full learning and proof fits each tiny slice.

**Roadblock:** Setup, resource finding, understanding, coding, running tests and independent explanation cannot credibly happen from zero for all those topics in 15 minutes. Repeated tiny pieces also magnify context-switching overhead.

**Minimal correction:** Merge nontrivial fragments into genuinely workable blocks (usually at least 30 minutes, often longer for first-time Kubernetes or design material). Make the week-row sentence say **which part** is taught in that box and reserve the code/test proof for the actual completion slot. Do not automatically increase every fragment; remove ambiguous repeated unit text first.

**Time / trade-off:** First rebalance existing week hours and check the continuity limits. If the teaching is still too large, use measured estimates and name the gate date that moves or the work displaced. **Evidence to close:** practical task + run + explanation fit the logged time.

### A4 | MEDIUM | Bedside review cards are not yet an enforceable retention mechanism

**Evidence from v3.8:** Sections 6.12 and 9 describe answer-first cards on day 1, 7 and 28 after a unit closes. They also say cards take zero scheduled hours, remain optional, and create no debt if missed. Section 5 correctly says *required* bedside work counts as learning time. Thus the cards can be useful, but the programme cannot claim they guarantee spaced retrieval.

**Roadblock:** If a hard-to-remember skill depends on voluntary cards that are quietly skipped, the original forgetting problem remains even while the plan looks complete.

**Minimal correction:** Make the choice explicit. **Option A:** cards are optional bonus recall; no score, no debt, and no claimed guaranteed coverage. **Option B:** if Om wants them compulsory, record actual minutes and fund them under the weekly capacity instead of calling them free. Keep the five-minute blank-page desk warm-up trial separate from optional phone cards.

**Time / trade-off:** A is zero counted hours; B consumes measured learner time and needs an explicit trade. **Evidence to close:** a clear statement of which mode is chosen and whether a missed card changes any proof obligations.

### A5 | MEDIUM | Early calibration interviews may precede the first spoken stories

**Evidence from v3.8:** W5 (Nov 2-8) opens low-stakes calibration applications. The first two written stories occupy later R2 slots and are first scheduled to be spoken with follow-up questions in W10 (Dec 7-13). The v3.8 change note implies spoken stories will be available before calibration interviews need them. The actual schedule cannot guarantee this.

**Roadblock:** Even a useful low-stakes recruiter conversation can ask for an impact story. Om may have technical material but no independently rehearsed explanation of his own contribution.

**Minimal correction:** Either move one short R2 *draft + spoken* rehearsal to the early calibration period (only after the story is accurate), funding it from existing R2/campaign time; **or explicitly call W5-W9 calibration exploratory diagnostics** where an unrehearsed story is permitted and logged as a baseline. Do not claim rehearsal was completed before the actual row provides it.

**Time / trade-off:** Moving, not adding, the existing R2 time is the default. If W5 preparation displaces campaign activity, note the exact hour and preserve the truthful project claims. **Evidence to close:** a recorded spoken story with two follow-up questions before a later non-diagnostic interview.

## Part B. Five broader strategic and execution risks

### B1 | CRITICAL: execution throughput and fragmented attention

**Plan evidence:** W4-W30 contains 27 weeks averaging 5.48 distinct non-routine track labels and 9.37 scheduled task segments per week, against a normal 12-hour capacity. Some weeks schedule eight non-routine tracks. The plan forecasts Gate A on 2 May 2027 and Gate C on 5 March 2028. The W2 close records about 13 hours of plan scope completed across the original 33-hour W0-W2 plan, and MC1 scored 2/10. That is a historical early snapshot, not a claim about current pace. The 5-minute warm-ups could add 28-45 hours across the plan; this is explicitly not included in the current 834.5-hour total pending the 15 November trial.

**Why this blocks the goal:** Having enough total hours on paper is not the same as closing tested units. At a *hypothetical sustained* eight effective plan-hours per week, 834.5 hours takes roughly 104 weeks instead of the draft's 75 calendar weeks. That would put completion around late 2028 rather than March 2028. It is a sensitivity calculation, not a prediction.

**Minimal response:** Keep the planned W4-W5 warm-up trial and track actual minutes from setup through passed proof. At the scheduled 15 November reforecast, report (a) active hours and (b) hours of units *proved closed* separately; quantify how much time track-switching consumes. Set the next month's weekly schedule from the observed pace. If eight distinct tracks in a week are causing repeated restarts, batch larger parts of related tracks together while preserving the continuity limit through small, explicitly funded recall. Don't pretend 12 hours of learner activity necessarily means 12 hours of closed plan scope.

**Cost / removal / trigger:** No new syllabus; audit is coach work. If warm-ups become mandatory, fund the measured 28-45 hours honestly with later gate dates or an explicitly displaced activity. Trigger: the already scheduled 15 November pace reforecast. **Priority: critical.**

### B2 | HIGH: independent human interview feedback arrives after applications start

**Plan evidence:** Normal applications begin W31 (3 May 2027). Mock 1 in W26 is with an assistant. The first scheduled *human* system-design mock is W49 (September 2027); the human live-coding mock is W61 (late November/early December 2027). Therefore there can be four to seven months of application activity before those external exercises are completed. Both are explicitly in the plan, just later than their strongest diagnostic value.

**Why this blocks the goal:** A coach familiar with the curriculum may not expose the same interruptions, ambiguities and communication pressure as a stranger. Hiring loops become the expensive first independent test. The existing Gate A unseen DSA set helps transfer, but it does not reproduce a human interviewer.

**Minimal response:** Make W26 Mock 1 a human design mock if a peer is available, retaining its existing three-hour box and taught-material bar; keep an assistant as backup if not. Bring the existing two-hour W61 human live-coding diagnostic forward to shortly after Gate A, before valuable referrals, while naming the two hours of campaign or other permitted work it displaces in that week. Do **not** add a fifth design mock just to solve timing.

**Cost / removal / trigger:** Human design mock: zero extra learner hours when replacing Mock 1. Human coding mock: move, don't duplicate, the existing two-hour slot, with a two-hour displacement where it lands. Recruiter-confirmed alternative formats remain a targeted adaptation. **Priority: high.**

### B3 | CRITICAL: no fallback if recent production coding ownership does not materialise

**Plan evidence:** The v3.8 draft carries v3.7's instruction to ask the IBM manager for owned Go/Python changes, target two meaningful changes by Gate B, quality over count, with a documented office proof path. However this is contingent on manager/team allocation. The October baseline records little independently written Go at work. The optional upstream PR is after OP7 and only if separately approved.

**External signal:** Current Datadog roles describe independent ownership of ambiguous problems, end-to-end production services, and Go development on Kubernetes; Stream's Amsterdam senior infrastructure role explicitly expects frequent code-writing and ownership of its platform migration. Relevant listings: [Datadog Incident Insights and Readiness](https://careers.datadoghq.com/detail/8247566/), [Datadog Compute](https://careers.datadoghq.com/detail/8139277/), [Stream Senior Infrastructure](https://jobs.ashbyhq.com/stream/d86db37b-1a62-415c-91be-d7c7e5f0d36b/). These are examples, not statistically representative of the whole market.

**Why this blocks the goal:** A polished personal repo demonstrates skill but cannot legitimately be sold as years of recent production implementation. If IBM cannot allocate end-to-end feature work, the plan has no dated fallback for this hiring-screen risk. Two tiny changes also would not necessarily repair it.

**Minimal response:** Make an **office, not study-hour**, checkpoint at the next objectives discussion: seek one meaningful owned feature or substantive code path with explicit manager agreement. Re-check by the W7 close and again at Gate A. If blocked, pursue real implementation ownership in another appropriate IBM workstream, an internal move where realistic, or a substantive externally reviewed OSS contribution, while explicitly labelling the latter non-production. If the professional evidence remains thin, adapt the primary job-search lane and CV claims to genuinely demonstrated strengths rather than implying recent backend service ownership.

**Cost / removal / trigger:** Zero scheduled study hours for the manager discussion; any personal OSS project takes real hours and needs a separate one-in/one-out decision. Trigger: manager says no, no feature is assigned, or no substantive code path is owned by the Gate A review. **Priority: critical.**

### B4 | HIGH: international funnel measures matching words rather than accessible roles

**Plan evidence:** The November JD harvest records regional fit, English-language requirements, production experience and duties, and Gate B's region decision. But it does not explicitly distinguish roles an India-based candidate may actually apply to and join from roles limited to people already in the EU or local country. Main India/international parallel applications only begin after Gate B on 6 February 2028, and the plan notes the three-month notice period and the practical September 2028 latest-acceptance line for starting in 2028.

**External signal:** Stream's Amsterdam posting offers Amsterdam hybrid or remote EU, whereas other EMEA roles use different geographic language (for example [Percona Senior Backend Go](https://jobs.ashbyhq.com/percona/94c8439d-9db3-4238-a073-9c21a0409e90)). An English-speaking listing is not, by itself, proof that hiring from India is supported.

**Why this blocks the goal:** The harvest could count opportunities that are not realistically accessible in Om's circumstances, giving a misleadingly healthy regional funnel. Delayed discovery of geographic eligibility can squander the limited 2028 search window. Separately, the explicitly approved 'first strong offer wins' rule can result in an India offer and a later overseas move, a known trade-off rather than a plan bug.

**Minimal response:** Add to the *existing* W6-W7 and W58 JD-harvest data, not a new research track: **location requirement, evidence of accepting India-based applicants, relocation openness where published, and unknown vs confirmed status**. Keep unknowns unknown. Only confirmed-accessible or plausibly accessible roles should count towards the international funnel's usable target count. At the W7 close, if too few credible roles remain, reconsider lane or country targeting using evidence before valuable referrals are spent. Preserve Om's already approved first-strong-offer rule unless he explicitly changes it.

**Cost / removal / trigger:** Additional classification is coach research work, outside Om's counted learner hours under the existing three-clocks rule; Om still spends only the already allocated harvest decision time. Trigger: November harvest reveals weak or unknown eligibility among the top roles. **Priority: high.**

### B5 | HIGH: plan revision itself is becoming an execution risk

**Evidence:** Changes moved rapidly from v3.4 (19 Oct) to v3.5 (20 Oct), v3.7 (23 Oct) and the v3.8 draft (24 Oct). The earlier versions did miss genuine defects, so the recent work was not all waste. However the draft is now a 75-week, 834.5-hour, many-track programme. Each rebuild has further opportunities for sequencing, record, and cost inconsistencies. This risks diverting time from tested coding, speaking and applications.

**Minimal response:** After one consolidated critical fix pass, **freeze structure until the already scheduled 15 November 2026 reforecast**. Coach-discovered cosmetic defects go to the later-refactor log; do not open another broad external audit. A true untaught prerequisite blocking *this week's* work, evidence of repeated failed learning, or a major real market change can use existing section 9 change control. At the reforecast allow **one batch of measured changes**, with the original unit proof criteria protected. No change gets accepted because a further reviewer merely sees another possible improvement.

**Cost / removal / trigger:** Zero learner curriculum hours; saves learner and coach planning overhead. Trigger only under current section 9 approved change-control cases. **Priority: high.**

## What to fix now, and what not to change

**Before approving v3.8:** close A1 (untaught SQL), A2 (proof semantics), and A3 (unrealistic fragments). Make a one-line choice on A4 and A5. Decide how B2 will place a real human feedback loop early, and how B3's manager fallback and B4's accessibility fields will be recorded. None of this needs a new technology or wholesale rewrite.

**At the scheduled November 15 reforecast:** measure B1 using both Om's logged active minutes *and* the hours of actually closed, independently proved units. Use that evidence to budget mandatory warm-ups honestly. Apply B5: one batch of measured corrections and then freeze until the next genuine plan trigger.

**Already present and worth keeping:** real coding in PRCP and the Go agent, kind work with PRCP's image, DSA cold practice, timed machine coding, spoken design, two-coach safeguards, live code proof, change control, and a conditional extras queue. These should not be sacrificed just to make dates look earlier.

## Not recommended

- No new Kafka, Redis, extra cloud, AI topic, certification, or study resource without the plan's JD/loop trigger.
- No claim that personal PRCP commits are IBM production experience.
- No redundant scored quiz programme on top of existing DSA and unit proof rules.
- No treating a green static checker, completed hours, or an interview calendar as a readiness verdict.
- No override of the already approved India-plus-international, first-strong-offer decision merely because a coach prefers another strategy.

## Final recommendation

Accept **one consolidated patch list covering A1-A5 and B1-B5**, have Claude merge it into the v3.8 draft under existing change control, run the full checker and negative tests again, and let Om approve or reject the final draft. Then stop revisiting the syllabus until evidence requires it.

**Success condition:** Om can independently produce, run, debug, explain and defend production-grade code, perform in an unfamiliar interview, and demonstrate credible ownership to an actual employer. The 834.5-hour plan is only a means to that end.
