**Type:** GAP. **Affected plan:** sections 2, 5, 6.1, 6.5, 7 and 14.

Your account separates three things: earlier hands-on building, later client/delivery management, and the current rebuilding period. The plan's sentence “Engineering judgement is at level; tool fluency ... is not” is too broad for that history.

The recorded Python baseline, MC1 result and later teaching observations support specific gaps. Credit demonstrated knowledge; teach only the specific missing prerequisite.

### The sequencing problem

The plan already teaches selected Python prerequisites inside P1 and OOP concepts in L1. That is good. However:

- P1 and early LLD use objects, tests and state while the “classes from the ground up” part of Y8 is in W26.

For example, before a repository class, establish that you can explain and change an object holding a connection. Before a yield fixture, teach the required generator behaviour. Do not require the full generators chapter, MRO or garbage collection first. Credit the L1 material already taught and checked in October.

### What learning research supports

The [Cepeda et al. meta-analysis](https://www.yorku.ca/ncepeda/publications/CPVWR2006.html) supports distributing practice over time and shows that useful spacing depends on the desired retention interval. [Karpicke and Roediger](https://profiles.wustl.edu/en/publications/the-critical-importance-of-retrieval-for-learning/) found delayed recall benefits from retrieval after initial success. [Rohrer and Taylor](https://digitalcommons.usf.edu/psy_facpub/1767/) found advantages for spaced and mixed mathematics practice.

These studies support retaining and revisiting learned skills. They do **not** identify an optimal weekly Go/Kubernetes split for you. Applying them to this engineering plan is an inference to test, not a scientifically established timetable.

## 6. F3: harden the role filter before adding technologies

**Type:** GAP. **Affected plan:** sections 1, 3, 5, 6.2–6.4 and 8.

### The loophole

The plan's November harvest is directionally right. Its global technology-frequency trigger is too blunt unless the denominator and requirement strength are recorded.

A job mentioning Python, Go and Kubernetes can still be Java-first, authentication-specialist, data-pipeline-heavy, frontend-heavy or sustaining support. J6–J12 provide concrete examples. Counting those equally would create a curriculum for a job you do not want.

Likewise, a hard requirement in a small group of highly relevant control-plane roles can matter even if it never reaches 40% of a mixed backend/platform sample.

### Recommended harvest record

Record these fields for each posting:

| Field | Why it changes the decision |
| --- | --- |
| Employer, requisition, canonical URL, location, retrieval date and availability | Avoid duplicates, expired postings and accidental geography changes. |
| Actual work and expected coding ownership | Separate building services from operating/configuring someone else's system. |

## 7. F4: move the feedback loop closer to the work

**Type:** GAP. **Affected plan:** sections 4, 6.1–6.5, 7 and 14.

### What already works

Section 7 already requires explanation, planted bugs at milestones/gates, and a change or hidden bug under pressure. v3.5 already adds unseen DSA sets. These are strengths. I am not proposing them as missing features.

The problem is when ownership and integrated behaviour are checked:

- Y7's complete pre-plan PRCP code walk waits until W47–W48.
- D1 starts in W25.
- The Go agent starts in W25.
- The full three-part kind deployment starts in W41.
- The first scheduled design mock is W39.
- MC3–MC5 cluster in W28–W30, then MC6 waits until W50.

The learning sequence is long enough that a correct isolated component can wait months before meeting the conditions that expose its weakness.

### A tighter path using the same project

1. **P1:** get one existing PRCP use case all the way through persistence. Trace the request, validation, repository operation, result and failure. Complete the remaining repository scope, rather than replacing it with a smaller permanent syllabus.
2. **Before editing a pre-plan module:** explain its small relevant path. Move that part of Y7 forward. Keep a later whole-system cold walk.
3. **After sufficient Go HTTP/testing prerequisites:** build A1's sequential agent. It does not conceptually need goroutine teaching first. A2 does. Changing the current A1-after-G7 dependency requires an approved plan/checker amendment.
4. **After container basics:** run the API/database first; add the agent when ready. Do not make the first useful deployment wait for every component's final packaging.
5. **Design:** use early H1/H2 work to defend the choices actually being made. Reserve full mocks for when the needed building blocks have been taught.
6. **MC:** keep short skill practice tied to observed defects; decide how to spread the six full reps from its measured results.

This is staged feedback, not permission to test untaught topics or to label a local demo production-grade.

### Acceptance cases worth making explicit

These strengthen existing units. They are **proposed proof cases, not discovered PRCP defects**.

| Existing unit | Case to attach after its prerequisites are taught | Why |
| --- | --- | --- |
| P1 | A failing operation leaves the database in the specified state; a committed operation survives a new connection. | Avoid proving only that a mocked function was called. |
| P4 | Old and new app versions both operate during the migration, with an explicit rollback boundary. | An upgrade/downgrade command alone does not prove compatibility. The plan already asks for coexistence; preserve that bar. |
| A1/A2 | A slow probe times out; cancellation finishes; the active probe count stays bounded. | A clean race-detector run does not by itself prove these behaviours. |
| A3 | Two simultaneous deliveries with one idempotency key, and a lost response followed by retry, create the specified durable outcome. | A serial duplicate test can miss a concurrency defect. |
| A4/D2 | Shutdown stops taking work and handles in-flight work according to an explicit time limit. | “Received SIGTERM” is weaker than the promised behaviour. |
| S5 | Define who may configure a probe target and which destinations are allowed for the intended environment. | A service that fetches supplied URLs needs a deliberate target-access policy. |

The [Go race detector documentation](https://go.dev/doc/articles/race_detector) explicitly limits detection to runtime paths exercised. [PostgreSQL's INSERT documentation](https://www.postgresql.org/docs/current/sql-insert.html) describes unique-index conflict handling and atomic upsert behaviour; the whole ingestion transaction still needs a defined contract. [OWASP API7](https://api-security.owasp.org/editions/2023/en/0xa7-server-side-request-forgery/) explains risks from server-side fetching of supplied URLs. Internal probes may legitimately need private destinations, so blindly banning all private addresses is not the answer.

For ownership, choose a few expected outcomes from the requirements yourself before AI drafts broader tests. Keep the original notes. This complements the existing AI rules; it does not require writing every production test unaided.
